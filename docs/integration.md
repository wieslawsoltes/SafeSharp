# Installation, configuration, and releases

## Packages

The current package version is `0.4.0-preview.1`. Building a package does not publish it. Until a NuGet release is published, install the packages from `artifacts/packages` or a downloaded CI artifact. Use a clean package output directory when changing versions so consumer validation cannot select an older build.

```xml
<ItemGroup>
  <PackageReference Include="SafeSharp.Analyzers" Version="0.4.0-preview.1" PrivateAssets="all" />
  <PackageReference Include="SafeSharp.Contracts" Version="0.4.0-preview.1" />
  <!-- Optional IDE fix for explicitly acknowledging MustUse results. -->
  <PackageReference Include="SafeSharp.CodeFixes" Version="0.4.0-preview.1" PrivateAssets="all" />
</ItemGroup>
```

The analyzer and optional code-fix assemblies are under `analyzers/dotnet/cs`, not `lib`. `SafeSharp.Core.dll` is adjacent to the analyzer so the compiler can resolve its implementation dependency. The analyzer package does not bundle Roslyn; it uses the compiler host. Contracts target .NET Standard 2.0 and are a small runtime reference with no dependencies, including the TypeLifetime/TypeOutlives and GuardedBy/RequiresLock annotations. Their marker methods preserve reference identity and do not enforce exclusive access at runtime.

Analyzer/CodeFixes target .NET Standard 2.0 and Roslyn 4.14 APIs. Use a compiler/IDE hosting Roslyn 4.14 or newer; .NET 10 is the tested SDK. The package smoke check additionally runs analyzer discovery and the exported code fix inside an independent Roslyn 4.14 host. The .NET tool targets .NET 10 and uses newer Roslyn Workspaces independently of the analyzer's minimum host API. Visual Studio, Rider, and command-line `dotnet build` surface compiler analyzer diagnostics when analyzer execution is enabled. IDE-specific visual integrations are not required: source-linked HTML, DOT, Mermaid, JSON, and SARIF are generated by the separate tool.

## Build and validate

```sh
dotnet restore SafeSharp.sln
dotnet build SafeSharp.sln -c Release --no-restore
dotnet test tests/SafeSharp.Tests/SafeSharp.Tests.csproj -c Release --no-build
python tests/cli/verify.py --tool src/SafeSharp.Tool/bin/Release/net10.0/SafeSharp.Tool.dll
dotnet pack SafeSharp.sln -c Release --no-build -o artifacts/packages
python eng/verify-packages.py artifacts/packages
python eng/smoke-consumer.py artifacts/packages --version 0.4.0-preview.1
```

The consumer smoke check restores real NuGet packages in an isolated SDK project and fresh package cache. Its safe example exercises named return/delegate lifetimes, a nested callback tied to its outer capture, stored factory results, observed deferred disposal, reusable AsTask results, direct-call type lifetimes, disposal through a canonical array ref, access under a readonly object/Monitor guard, a SemaphoreSlim guard across await and valid Send/Sync structure. The unsafe example must fail with `SS0001`, `SS0003`, `SS0017`, `SS0021`, `SS0027`, `SS0041`, `SS0044`, `SS0045`, `SS0047`, `SS0048`, `SS0049` and `SS0050`. This covers ownership, possible async production loss, cleanup, borrowed retention, nested placeholder leaks, missing direct-call evidence, canonical array/ref use after disposal, ValueTask reuse and unguarded Monitor/semaphore access.

The check installs the packaged .NET tool and verifies the same findings and exit code in standalone source and MSBuild project modes. It checks universe visibility/promotions, consumed capability certainty/provenance, required/held Monitor/semaphore guard metadata, direct-call obligation metadata and cached async result identity. Project mode exercises the packaged build host and installed-SDK resolution, suppressed exhaustion from an MSBuild budget property exposed by the package, and EditorConfig precedence over that property.

The separate `eng/package-host` fixture loads the packaged analyzer assembly through Roslyn 4.14's analyzer discovery API, composes the packaged C# code-fix export with MEF, obtains a real `SS0024` diagnostic, applies its registered action, and recompiles the changed document. It retains the changed syntax tree instead of reparsing the resulting text, so malformed contextual tokens cannot be hidden by a fresh parse. The same fixture executes ownership, universal and higher-ranked region problems through the `SafeSharp.Core` package. It serializes an ownership finding and renders a computed nested placeholder leak, including its static upper-bound node, through `SafeSharp.Reporting`. Real `SS0049` reports must also retain the required Monitor/semaphore guard and empty observed capability state, while `SS0050` reports retain direct-call requirements and related contract evidence. Valid/invalid method groups and lambdas, outer-capture lifetime binding, stored/repeated async results, ValueTask consumption/reusable conversion, Monitor/semaphore guarded access, direct-call lifetime obligations and canonical array/ref disposal all run on the minimum supported Roslyn host. The guard fixture uses a readonly object, so the annotation API and analyzer compatibility checks do not depend on System.Threading.Lock. These checks cover all six packages and catch missing dependencies, omitted analyzer entries and export/load failures that direct unit tests do not.

Package verification checks that all six IDs share one release version, all six matching symbol packages contain portable PDB metadata, bundled SafeSharp assemblies match the corresponding library packages byte for byte, analyzer packages contribute no runtime dependencies, and the tool supplies its build host without bundling SDK-owned MSBuild assemblies into its runtime directory.

The fresh-consumer gate can also run without a network connection when the third-party NuGet dependencies are available in a local feed:

```sh
python eng/smoke-consumer.py artifacts/packages --version 0.4.0-preview.1 --dependency-feed /path/to/dependency-feed
```

This still creates a fresh package cache. Package source mapping restricts `SafeSharp.*` to the release feed being tested, so a previously cached or separately published SafeSharp build cannot satisfy the gate. Omitting `--dependency-feed` uses nuget.org for third-party dependencies, as in CI.

Both consumer builds explicitly select their generated NuGet configuration. This prevents inherited source mappings from overriding the dedicated SafeSharp feed, including when an offline dependency feed contains an earlier build with the same preview version. The fresh cache and explicit source mapping are separate checks. This uses MSBuild's documented [`RestoreConfigFile` property](https://learn.microsoft.com/en-us/nuget/reference/msbuild-targets) and [explicit NuGet configuration selection](https://learn.microsoft.com/en-us/nuget/consume-packages/configuring-nuget-behavior).

## EditorConfig

```ini
[*.cs]
# Promote concrete violations to build failures.
dotnet_diagnostic.SS0001.severity = error
dotnet_diagnostic.SS0004.severity = error
dotnet_diagnostic.SS0006.severity = error

# Optional boundary auditing; these are disabled by default.
dotnet_diagnostic.SS0032.severity = suggestion
dotnet_diagnostic.SS0033.severity = suggestion

# Ownership flow budgets; exhaustion produces SS0015.
safesharp_max_iterations = 10000
safesharp_max_tracked_resources = 2048
safesharp_report_possible_issues = true
safesharp_check_suspension = true

# Named/nested regions, type lifetime relations and return provenance; exhaustion produces SS0043.
safesharp_max_regions = 256
safesharp_max_region_constraints = 4096
safesharp_max_region_steps = 100000

# Aggregate cleanup, concurrency/guard capabilities and borrowed escape; exhaustion produces SS0046.
safesharp_max_contract_steps = 20000
```

Ownership and lifetime budgets bound each analyzed method; contract budgets independently bound the corresponding cleanup, structural/callback, synchronization or borrowed-escape check. Invalid settings fall back to defaults, and excessively large budgets are clamped. Lifetime settings cap at 4,096 names, 100,000 constraints and 10,000,000 steps; contract steps cap at 1,000,000. File-specific configuration takes precedence over global analyzer configuration. Additional structural limits are documented in the [region guide](lifetime-regions.md), [higher-ranked solver](higher-ranked-regions.md), [type lifetime contracts](type-lifetimes.md), [reference storage](reference-storage-analysis.md), [aggregate/concurrency guide](aggregate-concurrency.md), [synchronization guide](synchronization-analysis.md), and [borrowed-escape guide](borrowed-escape.md).

`safesharp_report_possible_issues = false` hides possible findings from the ownership dataflow engine; it does not strengthen the analysis guarantee. Semantic contract diagnostics such as SS0027 use their own standard per-rule severity/suppression settings. Use ordinary `#pragma warning`, `SuppressMessage`, or EditorConfig suppressions only after assessing the related acquisition and effect evidence. Generated source is skipped, and analysis honors cancellation. The analyzer never writes graph files during an IDE/build compilation.

The analyzer package exposes `SafeSharpMaxIterations` and `SafeSharpMaxTrackedResources` as compiler-visible MSBuild properties. Set them in a project or `Directory.Build.props` for shared defaults; file-specific EditorConfig budget values take precedence. For example:

```xml
<PropertyGroup>
  <SafeSharpMaxIterations>10000</SafeSharpMaxIterations>
  <SafeSharpMaxTrackedResources>2048</SafeSharpMaxTrackedResources>
</PropertyGroup>
```

The CLI uses the workspace's analyzer configuration and distinguishes configured diagnostics from raw engine evidence. SS0015, SS0029, SS0043 and SS0046 mark incomplete ownership, service, lifetime or contract analysis. Any of these makes the report incomplete and returns exit code 2, including when that diagnostic is suppressed or `--fail-on none` is selected. The CLI integration tests exercise all four exhaustion producers across per-rule, category and global severities, pragmas, `SuppressMessage`, `NoWarn`, and warning-level configuration. The report still honors the original severity and visibility settings. See [reporting](reporting.md) for formats and command options.

## Trusted publishing on nuget.org

The repository contains a complete `release.yml` workflow using NuGet OIDC trusted publishing. It builds and validates the exact version before requesting a short-lived publishing credential. No long-lived NuGet API key is needed.

1. On nuget.org, create or select the account/organization that will own `SafeSharp.*`. Verify the package names are available for that owner.
2. Under **Trusted Publishing**, create a GitHub policy with repository owner `wieslawsoltes`, repository `SafeSharp`, workflow filename `release.yml` (filename only), and environment `nuget`.
3. Give the policy permission to create/update the intended `SafeSharp.*` package IDs, and select the correct package owner.
4. In GitHub repository settings, create the Actions environment `nuget` and set the repository or environment variable `NUGET_USER` to the nuget.org **profile name**, not an email address.
5. Dispatch **release-nuget** with a version such as `0.4.0-preview.1`, or push a matching `v0.4.0-preview.1` tag. The tag must identify the intended reviewed main commit.

The workflow validates the version, restores, builds, tests, packs all six packages, validates their contents, exercises a real package consumer, and uploads the package artifact. Only then does `NuGet/login` exchange the workflow identity for a short-lived API key and publish packages/symbols. NuGet account policy creation and the first publication are separate account operations; neither happens just by committing this workflow.

References: [NuGet trusted publishing](https://learn.microsoft.com/en-us/nuget/nuget-org/trusted-publishing), [analyzer package layout](https://learn.microsoft.com/en-us/nuget/guides/analyzers-conventions), [Roslyn analyzer configuration](https://learn.microsoft.com/en-us/dotnet/fundamentals/code-analysis/configuration-options).

The benchmark console project is excluded from all NuGet packages. CI runs the `all` suite with one informational timing sample: independent liveness equivalence checks and expected-result checks for the current higher-ranked lifetime, reference-storage and composed ValueTask scenarios. The newer boundary scenarios have no historical implementation baseline. Correctness and package compatibility are gates; wall-clock speed ratios are recorded measurements, not pass/fail assertions. See [performance](performance.md).
