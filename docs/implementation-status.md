# Implementation status

The `0.3.0-preview.1` implementation contains 40 diagnostics, five compiler analyzers, a reusable Core engine, five report formats, and six NuGet packages. This page records the implemented mechanism and the boundary of each claim. It describes the current source and package payloads; ordinary C# retains its own language and runtime semantics.

## Deliberate precision boundaries

These are material limitations of the current implementation. They must remain visible when extending the analyzer or assessing a clean report.

- **C# runtime semantics:** assignments can copy structs or alias references; annotations do not revoke runtime access. `Owned` does not create a move-only CLR type. The C# compiler remains responsible for definite assignment, ref safety and language restrictions.
- **External behavior:** an unknown virtual/native/reflection/dynamic call can introduce aliases or effects absent from the model. Contracts are trusted at those boundaries. No whole-program or arbitrary heap-separation proof is claimed.
- **Summary inference:** source origin inference tracks ref-local aliases, conditional reference targets and ref reassignment. Bodies with exception handlers, unknown ref-return storage, arbitrary callback effects and recursive virtual dispatch remain conservative. General external ref-slot postconditions require contracts; uncertain writes retain unknown origins.
- **Borrowed escape precision:** SS0027 reports possible retention of a declared borrowed/no-escape input, with source/destination evidence. Allocation containers merge fields/elements, and handlers and mutable captured cells use conservative envelopes. Unknown calls do not establish either general retention or freshness. This is not a complete heap-shape or concrete escape-path proof.
- **Async result factories:** stored owned `Task<T>`/`ValueTask<T>` factories and known completed producers preserve one result identity. A factory fault does not allocate a successful result. Arbitrary task combinators, custom awaitables/builders and full ValueTask single-consumption rules need additional models; task identity alone does not prove payload provenance.
- **Cleanup and faults:** recognized invocation discharges the original release obligation; observed completion discharges the asynchronous observation obligation. Neither proves successful physical cleanup by a throwing implementation. Aggregate checks cover modeled normal exits, not all exceptional termination or cross-call object invariants.
- **Regions:** explicit named signature constraints and one universal delegate binder are supported. Nested universes, placeholder leak checks, arbitrary generic variance, implied type bounds and Rust's full higher-ranked type/trait solving are not reproduced. Unknown returned provenance cannot satisfy a lifetime promise.
- **Concurrency:** Send/Sync are explicit C# contracts, with structural checks and recognized boundaries. They do not provide Rust auto traits, prove arbitrary synchronization or races, or establish CLR memory-ordering and native-pointer properties.
- **Unsafe/address behavior:** pinning, self-referential state-machine validity, raw-pointer provenance, `UnsafeCell`, stacked/tree borrowing and atomic order proofs are outside the analysis.
- **Abstract allocation identities:** distinct fields can remain independent, but general symbolic array inequalities, heap shape, collection element ownership and concrete per-iteration allocation counts are not solved.

## Incompleteness is observable

SS0015 identifies ownership-flow limits; SS0029 identifies service exploration limits; SS0043 identifies lifetime solving/provenance limits; SS0046 identifies cleanup, concurrency and borrowed-escape contract limits. The CLI returns exit code 2 for an incomplete configured analysis even when these diagnostics are suppressed or `--fail-on none` is used. A solver budget is not a successful verification.

Adding another mechanism requires a defined transfer or contract rule, valid and invalid C# regressions, evidence/report support where applicable, and an update to this support boundary. Broader safety claims need demonstrated coverage and an explicit account of remaining approximations.
